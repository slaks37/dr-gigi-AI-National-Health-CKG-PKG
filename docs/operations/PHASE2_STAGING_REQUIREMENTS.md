# Phase 2 staging requirements and evidence boundaries

Date: 2026-10-24 (Asia/Jakarta). Scope: synthetic operational acceptance and an exact deployment checklist for an isolated, owner-authorized environment. Clinical use remains prohibited. Existing research Preview must retain `SONRI_RESEARCH_PREVIEW=1`.

## What can run without external credentials

`bash ops/staging/run.sh` builds the actual standalone Next app and private FastAPI worker, plus Firebase Auth/Firestore emulators. It requires Linux Docker Engine + Compose v2, Node 24 with repository dependencies, Chromium/Playwright system dependencies, and outbound build-time access to npm, Python packages, base-image registries and the official Firestore emulator download. Start with at least 4 CPU cores, 8 GiB memory and 16 GiB free disk for builds. This is an initial synthetic acceptance resource allowance, not measured clinical capacity.

The workflow `.github/workflows/container-staging.yml` runs the same script on an Ubuntu GitHub Actions runner. It needs only the ordinary read-only checkout token. It never reads deployment environments or secrets, enables a checkpoint, requests a GPU, starts training or deploys to production. The synthetic Firebase project ID is fixed as `demo-sonri-workflow`. Emulator listeners and app are bound to host loopback. Auth/Firestore are not substitutes for hosted Firebase provider/IAM validation.

The acceptance override enables `NEXT_PUBLIC_SONRI_EMULATORS=true` **at image build time**, because Next inlines browser environment variables. Merely setting that flag at container runtime cannot redirect a previously built browser bundle. Browser emulator mode is restricted by application code to `127.0.0.1` and `localhost`. Server SDKs address `firebase:9098` / `firebase:8088` over the container network; the browser uses host loopback. The production Dockerfile defaults the flag to false.

The app's `SONRI_RESEARCH_PREVIEW=0` override applies only to this loopback-only synthetic stack, which cannot address a real Firebase project. It does not modify the existing Vercel Preview or recommend clearing its guard. The private worker has no published port, uses a random ephemeral bearer credential of at least 32 characters, and has only the internal network. Its shipped registry keeps every checkpoint disabled. Model liveness, availability, raw-label semantics, dataset performance and clinical validation are different states.

## Executed acceptance versus supplied checks

Only a completed run with the tested Git SHA and artifacts establishes a pass. A workflow file or this document does not establish execution. `ops/staging/evidence/` is generated, ignored by Git, and uploaded as a sanitized CI artifact for 14 days.

| Evidence file | Check actually performed by the harness |
| --- | --- |
| `browser.json` | Real browser login with Auth emulator identities, patient consent/screening persistence, administrator case assignment, assigned clinician FDI odontogram/examination and confirmation, escaped report download |
| `acceptance.json` | Missing/malformed/disabled identity, forbidden administrator actions, cross-patient record/screening/report/exam access, unassigned clinician, missing consent, stale assignment version, trusted-claim injection, direct Firestore audit forgery; audit/review/consent/revision persistence |
| `worker-boundary.json` | Health response, missing/wrong shared credential, authenticated private inventory, disabled-model rejection with no findings and clinical-use prohibition |
| `network.json` | Running worker has no published Docker ports |
| `restart.json` | App + worker restart, fresh emulator sign-in, case retrieval, private worker connectivity, unchanged six collection counts/hashes |
| `restore.json` | Auth + Firestore emulator export, emulator recreation/import, fresh sign-in, case retrieval, unchanged record/patient/audit/review/examination/consent collection counts and hashes |
| `observability.json` | Real worker request/status/latency/request-ID events exist and contain only the allowed fields; raw upload marker and shared credentials absent |
| `container-images.json`, `run.json` | Local image identities, execution time, exact CI commit and successful completion marker |

The temporary emulator export remains in a private Docker volume and is removed on exit. Raw emulator logs can contain synthetic sign-in tokens and are not uploaded. The log checker uploads aggregate observations, not raw worker logs. Evidence contains no patient images or identifiers and is not a clinical benchmark. The restore test establishes only the synthetic emulator mechanism; it does not establish managed Firestore backup/export restoration. External alert delivery, forced native model hangs, real load testing, host outage and managed-service failover remain separate acceptance requirements.

## Exact owner-authorized hosted Firebase staging requirements

Provisioning is pending until the owner provides the following nonsecret identities/approvals and secure access. Do not reuse the production/research Firebase project or copy patient data into staging.

1. **Project and billing scope:** a new or existing dedicated Firebase/GCP staging project ID, project number, approved organization, region, billing/quota decision, selected Firestore database ID and operator with project-creation/administration authority. Create an empty database. Confirm the chosen location before creation. No infrastructure purchase is implied by this document.
2. **Browser app registration:** register a Web app in that staging project and obtain its public Firebase browser config. The current application imports `firebase-applet-config.json`; setting only `GCLOUD_PROJECT` does not change the browser project. Until a deployment configuration adapter is added, build from a private staging copy with that file replaced by the approved staging Web-app config and consistent `firestoreDatabaseId`. Never deploy a mixed browser/server project build. The resulting image must be marked staging and must not be promoted to production.
3. **Auth settings:** explicitly enable only approved sign-in providers, configure authorized staging domains, provider credentials through the owner's secure channel when required, and provision synthetic identities. For the initial acceptance use email/password synthetic accounts; provider OAuth flows require their own hosted verification. Disable public use through the staging access control and organizational procedure. Verify disabled-user and token-revocation behavior against the managed provider.
4. **Trusted roles:** a restricted bootstrap operator with permission to manage Firebase Auth custom claims creates patient, administrator, assigned verified clinician, unassigned clinician and disabled synthetic identities. Claims are `role: patient|doctor|admin`; clinician confirmation additionally requires `clinicalReviewer: true`. Grant reviewer claims only after authorized professional/operator review. Dataset review requires separate `datasetScopes: ["SONRI"]`. Never take role or professional status from browser input.
5. **Firestore rules and identity:** deploy the reviewed `firestore.rules` to the staging database, and run the emulator rules suite first. The server workload identity needs staging-only Firestore read/write access (for example a constrained service account with `roles/datastore.user`) and the Firebase Auth read permissions needed for revoked/disabled-user verification. The bootstrap claims-management identity should be separate from the ordinary app runtime. Validate the final least-privilege permission set with denied-access logs; do not grant project Owner/Editor to runtime workloads.
6. **Server identity without a checked-in key:** use the host's attached service account / workload identity and Application Default Credentials. For a supported external workload, configure a narrowly scoped workload identity federation provider and service-account impersonation; the owner must supply the trusted repository/environment/subject constraints. A private read-only `GOOGLE_APPLICATION_CREDENTIALS` mount is a fallback only when securely provisioned and rotated. No service-account JSON is supplied or accepted in source/build arguments/browser environment.
7. **Image/storage scope:** the existing structured screening path records `source_images_retained: false` and does not require cloud storage uploads for its synthetic consent/odontogram/review/report journey. If durable study images are later authorized, provision an isolated private staging bucket, deny anonymous listing/reads, select retention and deletion rules, restrict service-account access and test consent revocation. Storage being named in browser config does not establish such a workflow.
8. **Build/runtime configuration:** use the same approved staging project for browser config and `GCLOUD_PROJECT`; set the exact `FIRESTORE_DATABASE_ID`; omit emulator flags/hosts from hosted managed-service builds; set `SONRI_INFERENCE_URL` and a distinct server-only `SONRI_INFERENCE_TOKEN`; preserve `SONRI_RESEARCH_PREVIEW=1` on the research Preview. Enable protected clinical-storage APIs only in the separate staging deployment after the isolated project and synthetic accounts are confirmed.
9. **Acceptance access and evidence:** provide a protected staging URL and an approved mechanism for synthetic test login, plus secure host access or scoped CI identity. Run the browser journey and negative tests against hosted services, record the application/image/registry/terminology hashes and examine managed Auth, Firestore and access logs. A local container pass does not complete this item.

## Private inference hosting requirements

Use an approved Linux host/network capable of Docker Engine and Compose; the supplied deployment keeps inference on a Docker `internal` network with no published worker port. Expose only the app through the owner's approved TLS/access gateway, and accept synthetic accounts only. The server and inference worker need a secret-manager reference for a distinct environment credential, not a browser variable. Mount an operator-reviewed registry at `/config/registry.json:ro` and a checkpoint directory at `/models:ro`; record exact hashes and rights before enabling a model. The existing CPU image supports the existing ONNX path; YOLO/PyTorch or future panoramic/CBCT adapters need separate reviewed images/dependencies and modality-specific limits. The default registry must remain disabled when artifacts/contracts/rights are unresolved.

Do not point this client directly at an IAM-protected cloud endpoint and assume the shared bearer token satisfies platform IAM. The current client sends the inference shared token, not a cloud workload identity token. That deployment needs a reviewed private network/proxy or an additional tested platform-auth adapter. Select an authorized host whose private routing matches the implemented contract.

Health at `/healthz` is process liveness. Validate the protected inventory separately; `available: false` is an operationally truthful failure state. Define host-level restart policies, memory/CPU ceilings, rate limits, maximum native inference duration, redacted request/status/latency metrics and an owner-approved alert destination. Test forced worker termination and app recovery before accepting loaded models. This Phase 2 harness tests restart/recovery with models disabled; it does not exercise a hung native model or GPU failover.

## Remaining external gates

Hosted project/identity/IAM/provider access, private inference host and secret-manager access, any authorized evaluation-image access, artifact licensing clearance, professional reference-label review, managed-service restore testing and clinical approval remain required independently. SATUSEHAT is unchanged and disabled; its approved sandbox credentials and submission/mapping evidence are separate. No clinical production deployment, training job, paid GPU allocation, patient-data migration or live clinician validation is performed by this harness.
